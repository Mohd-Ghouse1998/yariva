## Existing contracts and boundary

`Match.status=ACTIVE` is a mutual connection. No approved follow relationship existed, so `PrivateFollow` records requester, owner, and pending/approved status. A Like, inactive Match, or unapproved follow never qualifies. The existing `Block` relation is checked in both directions at each read. `Scene` is a public 12-hour activity object and stays separate. Existing profile-photo/Scene storage uses signed object URLs; those paths are not reused for private Story text or media. Reports accept an explicit Story target only after the reporter passes the same Story-read policy; a report opens the existing moderation case. Story events use the existing notification queue and durable deduplication.

## Decision

`PrivateStory` contains optional text, optional private media reference, owner, fixed 24-hour server expiry, selected/all-approved rule, optional community filter and deletion timestamp. `PrivateStoryGrant` snapshots recipient IDs at publication or confirmed edit. `PrivateCommunityPreference` stores optional identity, connection interests, and affirmative Story-community opt-ins separately. None derives from `UserDiscoveryPreference.preferredGenders`. Grants are bounded to 100 per Story. A community filter intersects approved grants with private opt-ins; the opt-in is checked again when opening.

The private-stories module owns audience resolution and the effective read rule. HTTP authorization is required. For a recipient, read requires an approved, active Story and both accounts active, no block in either direction, an active Match or approved incoming follow, a Story grant, and any community opt-in. Owner reads require an active owner account and active Story. Unprocessed media fails closed for everyone. Guessing an ID returns the same 404 as an absent Story. Feed rows use the same read rule; mobile displays no cached Story text until detail is rechecked. The viewer clears on background and rechecks on resume; expiry clears open content. Rail, management lists, fetched edit audiences and community choices also clear on blur/background and ignore stale async reads; new unsaved local drafts are kept. Community UI uses the existing English/Hindi/Telugu localization service. Audience preview returns only a count, never another person's labels. An all-approved audience is a publish-time snapshot. Audience expansion requires explicit confirmation, with grant replacement and Story edit in a serializable transaction. Approval and deletion are owner-scoped; follow removal has separate incoming and outgoing routes.

| Case | Access result |
| --- | --- |
| Owner, active Story | Read/edit/delete |
| Approved Match/follow and grant | Read while all other conditions remain true |
| Approved connection without grant | Deny |
| Grant without current approved relationship | Deny |
| Block either way, expired/deleted Story, inactive account | Deny |
| Community-filtered grant without current opt-in | Deny |
| Stranger, pending follower, past Match, guessed ID | Deny |

## Lifecycle and risks

Creation snapshots grants and sets expiry from server time. Edits replace grants; a removed viewer loses future reads immediately. Deletion is a soft delete and stops reads immediately. Already seen content cannot be recalled from memory or screenshots. Physical deletion runs daily for media and rows retained 30 days after expiry/deletion; unreferenced uploads are removed after one day. The worker uses bounded pages and retries object failures without deleting the row first. Photo and video uploads use a ten-minute signed PUT to a private object bucket under an owner-scoped random key. Creation checks size, MIME, owner/token metadata and signature, then bounded decoding/re-encoding strips source metadata/geolocation/chapters into a new private object and deletes the original. A Story detail request checks the full viewer policy before issuing a 60-second signed GET; image previews use a 10-second URL after the same policy check and no-store response. An already issued detail URL may work for up to 60 seconds after a block, follow revocation, deletion or expiry. A live test demonstrates this bounded limitation. Broad rollout remains gated.

New photos/videos start PENDING; only the owner can preview them until review. Text-only Stories use existing report/manual-takedown semantics. Media-caption edits return the Story to PENDING; audience-only edits preserve the decision. Existing media migrated to PENDING; existing text migrated to APPROVED. The existing ADMIN guard protects `/admin/moderation/private-stories` (opaque pending queue), `/:id` (audited content preview with short signed media), and `/:id/review`. Decisions require the exact `updatedAt` from the preview and compare it atomically, preventing approval of a changed caption or double decisions. Approval/rejection and content reads are audited. Rejection immediately denies recipient access and cannot be reversed by edits or approval; owners can delete. No automated provider verdict is claimed: until an actual moderation provider is configured, media stays pending for manual review. Reports use the existing case workflow; retained content follows the same 30-day policy rather than an indefinite evidence archive.

Story notices contain only generic copy and an opaque Story ID, with no author name, caption or community labels. Creation, inbox listing/read, queue dispatch and each device-token send recheck the Story policy and recipient rollout flag. Denied queued notices become CANCELED; inbox reads return the same 404. Mobile private notice rows clear on blur/background and refresh from the server on resume/realtime events. In-flight external sends and previously delivered generic system notifications cannot be recalled. APNs/FCM receipt remains blocked without credentials.

New text publication persists authorized, deduplicated PENDING notices in the same serializable transaction as the Story and grants. Media moderation approval persists its decision, audit record and notices together. A notice-persistence failure rolls back the transaction; concurrent moderation decisions produce one decision/audit/notice. The existing read policy accepts the transaction client to authorize uncommitted Story rows. Dispatch rechecks access after commit before emitting realtime events or enqueueing; inbox and delivery checks still apply after later revocation. Queue failure or process exit after commit leaves recoverable rows rather than losing the fanout. The existing generic notification persistence/dispatch implementation is shared through a leaf module to avoid a circular Story dependency. Legacy fanout jobs retain the same dedupe keys. This does not backfill notices lost before this change.

## 23 October session and operations follow-up

The authenticated mobile tree remounts on account identity changes. Authentication and HTTP operations capture a session version; late refreshes, responses and failures from an earlier session cannot replace or clear the current account. HTTP reports typed `409 SESSION_CHANGED` for obsolete work. Token persistence serializes saves and clears and waits for every key operation to settle, including partial failures, before beginning the next operation. This prevents an unfinished token write from repopulating storage after logout. Story lifecycle tests also prove that a delayed account-A feed cannot populate account B's tree. These controls supplement server authorization; they do not recall media already displayed or signed links already issued.

Story image/video error callbacks also capture the authorized read version, and media mounts are keyed per read. A native error queued before navigation/background cannot clear a newer authorized Story after navigation/resume. Current media failures still clear private content and Retry performs a fresh server read. Four reproductions failed before and pass after; focused viewer/lifecycle 20 tests and the earlier full mobile 54 files/244 tests passed. The other chat subsequently recorded its Scene composer integration fix and focused Android accessibility checks. A fresh combined-tree run now passes mobile typecheck/lint and 55 files/255 tests. Meet again reuses the existing plan flow. Participant checks, pair advisory locking, Match/DatePlan row locks, private answer writes, mutual outcome and two deduplicated notification intents run in one database transaction. Persistence failure rolls back the new answer and both intents. Notices are enqueued after commit; policy checks require a completed plan, an active match and active participants, two positive answers and no bilateral block. Listing, reading and sending reuse that check, so a queued result cannot reveal a now-revoked connection.

The worker schedules `notification.reconcile` every minute. Each pass re-enqueues at most 100 oldest PENDING, undeleted notices older than 60 seconds. The stable dispatch job ID deduplicates waiting/active jobs; retained completed/failed jobs can be retried. No exactly-once delivery or real provider receipt is claimed.
